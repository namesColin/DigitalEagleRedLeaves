## 一、项目概述

**数字鹰红叶**是一个 Windows 桌面 AI 数字生命项目。核心目标是创建一个具备**记忆**（Neo4j + Graphiti）、**视觉**（屏幕识别）、**人格**（RAG 对话）和**操作能力**（键鼠执行）的数字存在。

## 三、桌面自动化：试过的三条路线及失败原因

### 路线 A：纯 VLM 看图操作 ❌

```
截图 → VLM（Qwen/GLM/Agnes）直接输出坐标 → 执行
```

**测试模型**：GLM-4V-Flash、Agnes-2.0-Flash、Qwen-3.7-Plus、Qwen-VL-Max

**失败原因**：
1. **JSON 格式极度不稳定**——同一模型同一任务输出 6 种不同键名（`action`/`operation`、`element_id`/`target_id`、`click(N)`/`{"element_id":N}`）
2. **Qwen-VL-Max 画面理解好但坐标偏差 50-200px**
3. 免费模型（Agnes、GLM-4V-Flash）完全不可用，直接瞎判任务完成
4. 阿里北京端点频繁超时

### 路线 B：纯文本推理 ❌

```
截图 → OmniParser 检测 → 文本列表 → DeepSeek 推理 → 选编号 → 执行
```

**失败原因**：
1. OmniParser 标签 73% 是泛化描述（"a simple icon"、"a stylized tool"），DeepSeek 分不出哪个是 Chrome
2. 九宫格区域分组改善了一部分（"中上区域的长条形输入框"能推断是地址栏）
3. 但账号选择、特定应用图标仍需视觉分辨

### 路线 C：混合（Qwen 看图理解 + DeepSeek 结构化决策 + OmniParser 精确定位）⚠️ 差最后一步

```
截图 → OmniParser 画框带编号 → Qwen-VL 看图描述 → DeepSeek 输出 👆"element_id":3} → 执行
```

**这是最接近成功的方案。**

**Qwen-VL 画面理解已验证**：
- "当前是Chrome用户选择界面，左边Colin在[2]，右边Guest在[0]。建议点击[2]" ✓
- "当前是桌面，Chrome图标在任务栏[134]" ✓
- "当前Chrome已打开显示bilibili相关页面" ✓

**失败在最后一公里**：Qwen 说"Colin在[2]"，但执行时 [2] 的 OmniParser 标签是"a computer screen with writing tools"，不是 Colin 头像。标注图上有 80+ 框，Qwen 偶尔混淆相邻编号。

### 三条路线对比

| | 纯 VLM | 纯文本 | 混合 |
|---|---|---|---|
| 画面理解 | ✅ 好 | ❌ 看不懂标签 | ✅ 好 |
| 操作精度 | ❌ 坐标不准 | ✅ OmniParser | ✅ OmniParser |
| 输出稳定性 | ❌ 格式随机 | ✅ DeepSeek | ✅ DeepSeek |
| 编号匹配 | N/A | ❌ 分不出 | ⚠️ 70-80% |
| **整体可用性** | ❌ | ❌ | **⚠️** |

## 四、核心瓶颈

**把"视觉概念"映射到"屏幕像素坐标"这一层，暂无任何方案达到可用精度。**

这是一个视觉+空间+推理的综合任务——需要人类级别的空间对应能力来在 80+ 个标注框中选出正确的那一个。VLM（Qwen-VL-Max）已经非常接近，但在多框高密度场景下仍会混淆。
