# 浏览器操控方案最终报告

日期：2026-07-15 | 分支：experiment/three-layer-perception

---

## 一、问题

Agent 需要在 Chrome 中执行网页操作（打开、点击、输入、按键）。要求：快、准、不依赖白名单、不动用户默认 Chrome Profile。

---

## 二、路线探索

### 路线 1：Chrome 扩展 + chrome.debugger + HTTP 轮询

```
daemon ──HTTP── 扩展 ──chrome.debugger── 浏览器
```

**失败原因：** 每 CDP 指令有硬性延迟下限。

```
扩展 HTTP 轮询 GET /pop: 200ms
chrome.debugger.attach(): 500ms
chrome.debugger.sendCommand(): 300ms
chrome.debugger.detach(): 300ms
────────────────────────
每指令至少 1.3 秒。每步 3-5 指令 + DeepSeek 2 秒 = 每步 6-8 秒
```

尝试的优化均失败：
- 批量 /pop 返回全部命令：队列反而积压，daemon 发指令速度超过扩展处理速度
- JS 内 while 循环等元素出现：与 15 秒 timeout 冲突
- 合并多个查询为一次 evaluate：扩展通信模型是逐条指令，无法合并

### 路线 2：WebSocket 直连 chrome://inspect 端口

```
测试: Target.getTargets ✅
      Target.attachToTarget ✅（但返回的是事件而非结果）
      Runtime.evaluate ❌ Chrome 150 丢弃页面级指令
```

**结论：** Chrome 150 `chrome://inspect` 在协议层封了页面级 CDP 指令路由。

### 路线 3：Playwright connect_over_cdp

```
playwright.chromium.connect_over_cdp("http://127.0.0.1:9222")
→ /json/version → 404
→ Chrome 150 不暴露标准 DevTools HTTP 端点
```

### 路线 4：Playwright launch 独立 Chromium + 临时 Profile ✅

```python
p.chromium.launch_persistent_context(
    user_data_dir=tempfile.mkdtemp(),  # 临时目录
    headless=False)
```

| | 之前事故 | 这次 |
|---|---|---|
| 路径 | `C:\Users\yin\...\User Data`（默认） | `tempfile.mkdtemp()`（临时） |
| DPAPI | 路径变→解密失败→密钥被覆盖 | 无旧密钥，从零建 |
| Cookie | 全部丢失 | 不保留（关闭删除） |
| 用户 Chrome | 被污染 | 不碰 |

## 三、最终架构

### 每步流程（2-3 次 Playwright 调用/步）

```
① page.evaluate(汇总JS) → {url, title, bodyText, interactive[]}  [~0.1s]
② DeepSeek: 看摘要+目标+历史 → {action, target, js}             [~2s]
③ 执行:
   - click: page.evaluate(DeepSeek写的JS)   / 失败→坐标点击     [~0.1s]
   - type:  page.keyboard.type(text)                             [~0.1s]
   - navigate: page.goto(url)                                    [~0.1s]
   - scroll: page.evaluate("window.scrollBy(...)")               [~0.1s]
```

### 关键设计决策

**click 用 CSS 选择器。** DeepSeek 看页面元素列表（含 CSS 选择器），写 `document.querySelector('input.nav-search-input').click()`。不依赖像素坐标。

**type 用 Playwright keyboard。** `page.keyboard.type` 发真实键盘事件，Vue/React SPA 能正确捕获。JS `el.value='x'` 会绕过框架 getter/setter。

**搜索触发用 click 搜索按钮，不用 press Enter。** `page.keyboard.press("Enter")` 把 Enter 发给当前焦点元素——如果焦点丢失（SPA 重渲染）就无效。JS click 搜索按钮直接触发 SPA handler。

**一次 page.evaluate 汇总页面信息。** URL + title + bodyText + 交互元素列表 = 1 次调用，而不是 4 次。

### DeepSeek 输出格式

```json
{
  "action": "click",
  "target": "搜索框",
  "js": "document.querySelector('input.nav-search-input')?.click()"
}
```

## 四、验证结果

测试指令：`"打开B站搜索推理视频，点击第一个观看"`

| 步骤 | 操作 | 结果 |
|------|------|------|
| Step 1 | navigate bilibili.com | ✅ |
| Step 2 | click JS: input.nav-search-input | ✅ |
| Step 3 | type: 推理视频 | ✅ |
| Step 4-5 | 搜索触发 | ⚠️ DeepSeek 绕到 URL |
| Step 6 | click: .bili-video-card__info--tit | ✅ 视频卡片 |
| Step 7 | click: a[title="推理游戏"] | ✅ 精准命中 |
| Step 8-14 | 重复尝试 | ⚠️ Agent 未察觉任务完成 |
| Step 15 | done | |

B站搜索结果页点视频不是跳转到 `/video/xxx`，而是在当前页弹出播放窗——URL 只加了 `vt` 跟踪参数，标题不变。Agent 没察觉已成功。核心链路全部跑通。

### 对比旧方案

| 指标 | 旧（扩展+debugger+HTTP） | 新（Playwright） |
|------|------------------------|-----------------|
| 通信 | HTTP 轮询 | 进程内 CDP |
| 每 CDP 指令 | ~1.3s | ~0.1s |
| 搜索框能找到 | ❌ timeout | ✅ JS click |
| type 能生效 | ❌ timeout | ✅ keyboard.type |
| 任务完成 | ❌ 10分钟超时 | ✅ 15步完成 |
| 扩展依赖 | 必须 | 不需要 |

## 五、已知问题

- DeepSeek 有时候直接 navigate 到搜索 URL 而不是 click 搜索按钮 → prompt 可优化
- B站 搜索结果页点击视频后 URL 参数变了但 title 不变 → 用 bodyText 变化检测
- OmniParser 模型加载耗时 30 秒以上 → 纯浏览器任务不需要视觉模型，后续改为按需加载
