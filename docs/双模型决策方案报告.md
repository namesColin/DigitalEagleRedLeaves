## 一、要解决的问题

桌面 Agent 的终极难点：**把自然语言意图映射到精确的屏幕像素坐标。**

这个任务拆开看有四层：

| 层 | 问题 | 难度 |
|----|------|------|
| 视觉识别 | 屏幕上有哪些可交互元素？它们在哪？叫什么？ | OmniParser 已解决 |
| 空间理解 | 多个窗口重叠时，哪个是前台？元素归哪个窗口？ | 之前尝试用空间聚类，效果有限 |
| 意图匹配 | 用户说"选 Colin 登录"，屏幕上 80 个元素哪个是 Colin？ | **核心瓶颈** |
| 精确执行 | 把匹配到的元素转成鼠标点击坐标 | OmniParser 已解决 |

第二层和第三层是最难的。之前 9 条失败路线各有各的死法，但根因是同一个：**在逼模型做它不擅长的事。**

---

## 二、怎么解决的

### 2.1 空间理解：Qwen-VL 原图直看

**不做空间聚类，不做窗口检测，不做元素归属。** 把原始截图（无标注框、无编号、无 OCR 覆盖）直接发给 Qwen-VL。

```
输入: 2560x1600 原始 PNG 截图 + "描述当前画面"
输出: "Chrome 用户选择界面。左边是 Colin 账号的头像和名称,
       右边是 Guest。当前需要选择 Colin 登录。"
```

Qwen-VL 作为 VLM，天然具备 2.5D 空间理解能力——它看到的是真实桌面，自己能分辨哪些窗口在前、哪些在后、哪个元素属于哪个窗口。不需要任何额外处理。

**这解决了窗口层次问题**——不是因为加了个窗口检测模块，而是因为把空间理解卸载给了专门做视觉理解的模型。

### 2.2 意图匹配：DeepSeek 文本对齐

Qwen 输出的自然语言描述中提到了 "Colin"。OmniParser 的 OCR 检测到了文字 "Colin Carpet (MOUTAI...)" 并关联到了元素 [2]。

```
DeepSeek 输入:
  Qwen描述: "左边是Colin账号的头像和名称"
  元素列表: [2] "Colin Carpet (MOUTAI...)" (350,420) 80x80

DeepSeek 输出:
  {"action":"click","element_id":2,"reason":"Colin在元素2"}
```

这是**确定性的文本匹配**。"Colin" 对 "Colin Carpet"——不是模型在猜，是文本在匹配。DeepSeek 只是把这个匹配关系以 JSON 格式输出而已。

**这解决了意图匹配问题**——不是因为模型学会了桌面操作，而是因为把问题拆成了"看图说话 → 文本匹配 → 输出编号"三步，每步都是模型本来就擅长的事。

## 三、为什么之前 9 条路线全失败

### 3.1 纯 VLM 路线（4 个模型）

```
截图 → VLM → {"action":"click","element_id":3}
```

**死因**：VLM 的 JSON 输出格式极度不稳定。Qwen-VL-Max 同一个任务能输出 6 种不同键名（action/operation、element_id/target_id、带括号/不带括号）。解析代码追不上。

**教训**：不要让 VLM 输出结构化 JSON。

### 3.2 纯文本路线

```
截图 → OmniParser → 文本元素列表 → DeepSeek → 决策
```

**死因**：OmniParser 73% 的标签是 "a simple icon"、"a stylized tool"——DeepSeek 从这些文字里分不出 Chrome 和 VS Code。

**教训**：不要让纯文本模型做视觉决策。

### 3.3 混合路线（编号）

```
截图 → OmniParser 画框编号 → Qwen-VL 选编号 → 执行
```

**死因**：80 个彩色框挤在 640x400 缩略图上，Qwen 分不清哪个编号对应哪个图标。全分辨率 2560x1600 图网络超时。

**教训**：不要让 VLM 做精细的编号匹配。

### 3.4 混合路线（坐标）

```
截图 → Qwen-VL 输出近似 (x,y) → 最近邻匹配 OmniParser 框
```

**死因**：Qwen 输出的坐标 (715, 505) 距离最近 OmniParser 框 160px——这个框是 "a simple icon"，不是 Colin 头像。OmniParser 根本没检测到那个头像。

**教训**：坐标匹配的前提是 OD 框覆盖了目标。OOD（未检测到的元素）无法处理。

### 3.5 混合路线（OCR 双标注）

```
截图 → OD 框 + OCR 文字双标注 → Qwen-VL 看图 → 选编号
```

**死因**：标注图太大（全分辨率 + 双重标注），Qwen API 超时。图片缩小后文字不可读。

**教训**：不要让 VLM 同时处理标注框 + 文字叠加。信息密度太高。

### 3.6 纯规则（白名单）

```
关键词匹配 + 几何推断 + 特殊意图处理
```

**死因**：每修一个 bug 加一条 if，代码越来越长，覆盖面永远不够。遇到没见过的场景就卡住。

**教训**：规则写不完。

### 3.7 UI-TARS 7B 4-bit 本地

```
截图 → UI-TARS 7B 模型 → 操作坐标
```

**死因**：8GB 显存跑 7B 模型太勉强。精度 (ScreenSpot Pro 49.6) 不够可靠，推理速度太慢（40s 加载 + 每步数十秒）。

**教训**：本地 GUI Agent 需要更大显存。

## 四、最终方案的完整数据流

```
┌──────────────────────────────────────────┐
│              VisionAgent.run(goal)         │
│                                            │
│  每步循环 (最多 20 步):                     │
│                                            │
│  ① pyautogui.screenshot()                 │
│     → 2560x1600 PNG 原始截图               │
│                                            │
│  ② OmniParser V2                          │
│     ├─ model.analyze(img, "<OD>")         │
│     │   → {boxes, labels} (60-130 个框)    │
│     └─ model.analyze(img, "<OCR_WITH_REGION>") │
│         → {boxes, labels} (屏幕文字+坐标)   │
│                                            │
│  ③ _index(): 构建元素索引                  │
│     每个元素: {id, bbox, center,           │
│               od_label, ocr_text}          │
│     OCR 文字关联到 120px 内的 OD 框         │
│                                            │
│  ④ _decide(): 双模型决策链                 │
│     ┌─────────────────────────┐            │
│     │ Qwen-VL (原图,无标注)     │            │
│     │ → 自然语言描述            │            │
│     │ "Chrome用户选择界面,      │            │
│     │  左边Colin右边Guest"     │            │
│     └──────────┬──────────────┘            │
│                ↓                            │
│     ┌─────────────────────────┐            │
│     │ DeepSeek (纯文本)        │            │
│     │ 输入: Qwen描述 + 元素列表 │            │
│     │ 输出: {"action":"click",  │            │
│     │        "element_id":2}    │            │
│     └──────────┬──────────────┘            │
│                ↓                            │
│  ⑤ _exec(): 查 elements[2].bbox → 点击     │
│                                            │
│  ⑥ 验证: 2 秒后截屏对比像素变化             │
│     - loading: 画面在变, 等待               │
│     - static: 画面不变, 点错警告            │
│     - changed: 正常                         │
│                                            │
│  ⑦ ask_user 兜底: 双模型都失败时问用户        │
└──────────────────────────────────────────┘
```

### 为什么这个架构不依赖白名单

```
之前(白名单):
  输入 → if "chrome" → win_search
       → if "打开" → ...
       → if "网址" → ...
       → 每加一个场景加一条规则

现在(双模型):
  输入 → Qwen看图 → "Chrome用户选择界面,左边Colin...”
       → DeepSeek → "Colin→元素[2]→click"
       → 不需要规则——模型自己理解场景
```

Qwen 不需要知道"Colin"是什么意思。它只需要描述屏幕。DeepSeek 不需要知道屏幕长什么样。它只需要在文本中匹配 "Colin" → "Colin Carpet"。两个模型都不需要被训练或被教导桌面操作——它们分别在做自己最擅长的事。

## 八、路线图总结

```
纯VLM ❌ → 纯文本 ❌ → 混合(编号) ❌ → 混合(坐标) ❌
→ 混合(OCR) ❌ → 纯规则 ❌ → UI-TARS本地 ❌
→ 双模型(描述+匹配) ✅
```

**核心教训**: 不让任何一个模型做它不擅长的事。Qwen 只需要说人话，DeepSeek 只需要匹配文本，OmniParser 只需要给精确坐标。三个模块之间通过自然语言和结构化 JSON 解耦——模型不需要理解对方的输出格式，只需要做好自己的那一件事。
