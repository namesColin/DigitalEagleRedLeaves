> 日期：2026-07-13
> 状态：方案阶段，未实施

## 一、现状诊断

### 1.1 当前架构

```
pyautogui 截屏 → FastAPI HTTP → Florence-2-large (0.7B) → JSON 返回坐标+标签
```

`vision_model.py` 封装模型推理，`vision_server.py` 提供 API，`vision_client.py` / `vision_debug_view.py` 作为客户端。

### 1.2 发现并修复的问题

**问题一：推理极慢**

原始 `<OCR_WITH_REGION>` 耗时 **672 秒**（11 分钟）。

根因：

| 参数 | 改前 | 影响 |
|------|------|------|
| `num_beams` | 3 | 3 条并行搜索，每 token 3 次 forward |
| `max_new_tokens` | 1024 | 生成上限过高 |
| `use_cache` | False | 禁用 KV-cache（Florence-2 代码 bug，不能开） |

修复后：

| prompt | 修复前 | 修复后 |
|--------|--------|--------|
| OCR | 672s | 4.02s |
| OD | 3.57s | 0.26s |
| Caption | 崩溃 | 0.61s |

**问题二：坐标标注错误**

`vision_model.py` 的 `post_process_generation(image_size=(w,h))` 已将坐标转为绝对像素。但 `vision_debug_view.py` 又乘了一遍 `width/1000`，导致**双重转换**。

修复：去除 debug_view 的归一化乘法，直接使用模型返回的像素坐标。

**问题三：严重重叠框**

Florence-2 的 OCR 对单个 UI 元素返回大量重叠检测。实测一次返回 27 框，超半重叠在同一按钮上。

修复：添加 IoU 去重合并（阈值 0.5）。

**问题四：标签含模型 token**

标签含 `</s>` `<s>` 显示为乱码。

修复：渲染前清洗。

### 1.3 Florence-2 根本局限

| 局限 | 说明 |
|------|------|
| 非 UI 专用 | 通用模型，不认识 button/input/chat_area |
| 标签无意义 | 返回 "x" "×" 而非 "close button" |
| 重叠检测 | 无内置 NMS |
| 无空间关系 | 不知"密码框在用户名下方" |

## 二、候选方案

### 2.1 OmniParser V2（推荐）

| 维度 | 评估 |
|------|------|
| 架构 | YOLOv8（UI 专训）+ 可选 caption 头 |
| 速度 | ~0.6s/帧，约为 Florence-2 的 6-7 倍 |
| 标签 | 语义化：button、input、checkbox、link |
| NMS | YOLO 内置 |
| Windows | V2 已支持（V1 不支持，用户曾放弃） |
| 显存 | ~0.5GB |

### 2.2 Qwen3-VL 2B

单模型检测 + 理解。2B 参数，显存 ~6GB，速度慢于 OmniParser。

### 2.3 自训 YOLOv8（游戏场景）

长期自动化固定游戏时适用。100-200 张标注截图，训练 1-2 小时，推理 10ms/帧，精度 90%+。

## 三、推荐架构

```
第一层：FastAPI 服务（不变）
  vision_server.py — POST /analyze

第二层：检测引擎（可插拔）
  ├── OmniParser V2（通用）
  └── YOLO 自训模型（游戏）

第三层：语义理解（新增）
  LLM 将检测结果翻译为操作描述
```
